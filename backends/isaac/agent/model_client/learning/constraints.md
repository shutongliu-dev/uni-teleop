# Agent 自编技能约束设计

设计协议标识为 `agent_learning_constraints.v1`，不是已上线的运行 schema。本文件约束参与学习和评测的模型、它生成的 Python 程序，以及负责执行它们的宿主；不是限制项目开发者修改客户端源码的 AGENTS.md，也不表示这些保护已经实现。任务编号与学习权限按用户 2026-10-18 的澄清修正，task0 公开目标核对基于 `437750d`，已实现范围见 [README](README.md)，整体方案见[技能学习提案](../../../docs/agent_bench/skill_learning.md)。

设计目标是让 agent 在公开观测上自由编写、调试和积累技能，同时固定数据可见范围、物理权限与评测条件。规则必须由相应宿主或 bench 强制执行，不能只写进模型提示词。

**定义与自改进边界。**

| 对象 | 本项目定义 |
|---|---|
| agent 条件 | 固定模型及请求参数、宿主提示与上下文组装策略、工具/SDK、公开输入权限、控制轨道、依赖环境和预算；模型权重不更新 |
| learner / learning run | 一个独立学习者的一次完整开发历史；固定任务与条件，拥有自己的库、候选和累计成本 |
| skill / library | agent 写出的策略源码、参数、描述、检索资料和经验；skill 是条目，library 的完整不可变快照是 bundle，名字不是版本身份 |
| candidate | 某次发布内容及来源的记录；可被执行或验证，但发布不等于通过验证，更不等于选中 |
| slot / attempt / episode | slot 是计划中的一次练习或评价位置；attempt 是执行该计划的尝试，包含初始化失败；episode 是 bench 物理会话。成功初始化的 episode 才计入任务尝试，故障补跑保留原 slot |
| cell / action / intent | cell 是一次代码执行，可含多次操作；action 是有 ID 的物理操作；棋牌 intent 是落子意图元数据，不等于动作、落子或新任务 attempt |
| validation / selection | 前者按固定计划产生候选证据，后者依规则选择后续执行版本；两者都不是 agent 自报成功 |

`DEF-01`：RSI 可改的是自己的 skill/code、参数、长期笔记、自测和随 bundle 冻结的策略说明。不能改宿主权限提示、工具真实语义、框架/控制器、模型配置、物理、官方评分或预算；这些变化属于新实验条件。技能中的提示或说明属于数据，不能覆盖更高层规则。默认没有额外模型、外部检索服务或隐形并行学习者；若另设条件，必须预先登记其模型、权限和全部成本。

`DEF-02`：每次执行绑定 agent 条件身份、learner/run、任务/规则/release、初态、phase/slot/attempt/episode、bundle 与来源事件、临时代码 hash；双玩家任务另绑 match/player/robot/hand/turn。棋牌室 task1/task2/task3 使用其左右手身份，客厅 Task4 使用两套独立右手机器人的 front/rear 身份，不能只凭 `right` 区分所有权。恢复时核对这些身份，不用新 run ID 续接旧状态并重置成本。宿主合同含私有计划，模型只获得当前阶段的公开投影；不能把完整合同、其他槽位或凭据作为初始提示。

`DEF-03`：记录输入组装器、基础提示、历史压缩/截断与检索策略的版本，以及模型实际收到的公开输入。跨回合仅携带阶段允许的 bundle 内容；不能借摘要、缓存或检索记录绕过 reset。提供方无法固定后端模型版本时记录请求型号与可得响应标识，明确不可完全复现的部分，不伪造固定版本。

**规则来源与交付。**

任务规则、允许行为、成功/失败判定和评测协议由 bench 侧编写、版本化并发布，作为唯一权威来源。本文件是 agent 侧的接入与执行设计；涉及上述内容的条目是对接要求，不能代替 bench 的正式规则，也不能由学习 agent 自行补齐。客户端负责加载公开合同、校验版本并执行相应边界，独立评分与任务合法性检查仍由 bench 负责。

bench 在学习开始前应交付以下内容，具体字段名与载体由其公开协议确定。下述合同绑定是接口提案，尚未实现：

| 内容 | 需要明确什么 |
|---|---|
| 公开任务规则 | 目标、参与者与活动手、允许/禁止行为、成功与失败条件、终止和 reset 语义；涉及稳定保持、落子生效等条件时明确判定含义 |
| 公开交互与评测合同 | 可见观测、动作能力与限制、练习/验证/测试各阶段的反馈及持久化权限、预算计量和结果分类 |
| 可绑定的版本身份 | 可读说明与结构化合同对应同一规则版本，并与任务 release、执行校验和 evaluator 版本绑定；提供可核验的版本及内容哈希 |
| 一致性证据 | 公开合法/非法输入、成功/失败/终止示例及对应检查，证明说明、接口校验与评分采用同一份规则 |

`RULE-01`：宿主在 trial 开始前绑定 bench 发布的规则版本并归档公开合同；合同缺失、不支持、公开内容矛盾或与所选 release 不一致时拒绝进入正式学习/评测，不用客户端默认值或模型猜测补齐。规则变更需要新版本和新的运行条件；agent 自己形成的策略、自测和局部判断不能改写规则。公开说明应足以理解任务和判定含义，但私有状态、evaluator 源码与中间证据仍按信息边界隔离；公开规则与私有 evaluator 的一致性由 bench 验证。

Python 隔离、技能版本管理与模型调用监督由 agent 侧实现。实验选择的额外资源限制需要在运行配置中固定并披露；不能在客户端暗中增加任务禁令或改变成功条件。客户端错误和资源超限保留原始分类，如何计入评测由 bench 协议决定，不能自动解释成任务违规或失败。下文的学习阶段与预算方案仍需绑定 bench 发布的评测协议后才能作为正式比较条件。

**目录与责任。**

`agent/model_client/learning/` 保存 agent 框架与本约束。`bench/protocol/` 是 bench 的协议和校验层，`bench/runtime/` 是公开服务层；本次不在两处增加学习器，不修改任务、物理或评分。独立 `system0-system1/` 的私有 RPC、student 和抓取模板不进入默认学习能力。

开发使用项目外的独立 worktree，审查后通过 Git 集成。正式运行的框架来自冻结源码根；运行中生成的技能不是框架源码，不写回 `agent/`、`bench/` 或 `scenes/`。

| 实验目录示意 | 可见性与写权限 |
|---|---|
| `datasets/fr3_sharpa_bench/skill_learning/<experiment>/author/` | 本实验写技能的 agent 可通过受控工具读写；只含它自己的源码、参数和笔记 |
| 同实验的 `bundles/<content_hash>/` | 不可变技能包；执行进程只读选定版本 |
| 同实验的 `episodes/<episode_id>/scratch/` | 当前执行进程可读写；回合结束后不再向下一个回合开放 |
| 同实验的 `episodes/<episode_id>/public/` | 宿主写、当前回合只读；保存允许的观测与反馈 |
| 同实验的 `host/` | 宿主控制的发布事务、版本选择、计划槽位与验证证据；agent 仅获得按阶段投影的回执 |
| 同实验的 `audit/` | 操作者审计记录；学习进程不可直接访问，仅按阶段投影允许公开的记录 |

表中 datasets 是 `<开发存储>/datasets`。这是物理存储布局，不是给 agent 的完整挂载表；仅映射本阶段允许的子目录。资产仍在共享 assets，媒体仍在 `demo/interface/agent_demos`。不复制凭据、权重或大型资产进项目，不把整个 datasets、仓库或开发 worktree 暴露给学习模型。

具体布局与生命周期见[自进化库设计](storage.md)。每个独立 learner 使用独立实验库；结束回合时清空运行上下文并撤销旧目录访问，审计所需文件可保留。内容 hash 与候选/验证/选用状态分开记录，增加证据不改写已发布 bundle。

**角色与允许能力。**

| 角色 | 允许做什么 | 强制边界 |
|---|---|---|
| 写技能的 agent | 读公开 SDK 文档与本实验允许的经验；创建和修改技能、辅助模块、参数、自测与长期笔记；选择公开练习目标 | 源码工具仅操作它自己的工作区；无任意宿主 shell 或私有目录读取 |
| 技能 Python | 函数、类、自有模块、动态循环、异常处理、math/NumPy、公开 RGB-D 数组计算；回合内跨 cell 保留变量 | 固定依赖环境、受控文件系统和 IPC；无原生仿真句柄、宿主凭据或任意网络 |
| 可信宿主 | 模型调用、能力投影、版本加载、预算、动作收据、日志和 trial 调度 | 框架与运行配置冻结；agent 不能修改它的权限、计数器或日志 |
| bench | 公开契约、任务初态、原生执行、独立评分和物理审计 | agent 只能通过公布的机器人操作影响环境 |

不沿用旧 AST 语言对 `def`、模块、`while` 的统一禁止。循环和数值计算由进程级 CPU/wall/内存预算监督；自由编程不等于自由访问宿主。具体基础计算依赖在环境清单中固定；依赖更新必须重新生成运行合同，运行中不安装软件。

**信息与代码来源规则。**

| 规则 | 要求 | 执行位置 |
|---|---|---|
| `VIS-01` | 仅发布版本化 schema 允许的任务目标、规则、能力、RGB-D、本体、指令目标、机器人 FK、触觉/接触摘要及动作反馈；不返回原生字典、物体真值、评分中间量或私有错误栈 | bench 公开投影；宿主再校验和过滤 |
| `VIS-02` | 模型文字、图像、数组、缓存、工具返回和错误反馈使用同一输入条件；RGB-only 禁止 depth/point_at，tactile-off 移除触觉及 contact_history | 宿主统一投影 |
| `VIS-03` | 图片与深度校验 episode、revision、SHA、尺寸、时间和标定；不把旧帧标为新观测，不把缺失接触填零 | 观测代理 |
| `SRC-01` | 初始任务技能库为空。仅携入固定 SDK、通用数学能力和明确公开的机器人/传感器知识；所有初始提示词、示例、代码与资源登记来源 | 启动清单与来源检查 |
| `SRC-02` | 不默认携入任务 grasp/place 解法、成功轨迹、student 或人工修复方案。bench 公开且固定的 open/pinch_prepose 等机器人姿态可作声明过的基础先验，其接口/参数/资格进入条件，不算自主学得或已验证抓握 | 初始化与实验条件管理 |
| `FS-01` | 写代码的模型与执行 Python 使用同一信息边界；两者都不能读取 bench 源码、隐藏初态、其他实验/玩家记录、工程轨迹、运行凭据或审计根目录 | 工具代理及 OS 文件系统隔离 |
| `FS-02` | 文件读写只针对已授予的目录；拒绝路径穿越、链接逃逸及通过进程/环境信息读取宿主内容。固定包、所选技能和文档只读；执行 Python 的临时写入限 scratch，practice 中写技能的 agent 可经受控工具修改 author | 工作区代理与 OS 隔离 |
| `NET-01` | 执行程序不能自行建立网络或 Unix socket 连接，也无未监管子进程能力；模型调用和机器人操作全部经宿主预先绑定的受控 IPC | OS 隔离及 capability broker |
| `IPC-01` | IPC 只传经限额和 schema 校验的数据、源码与图像数组，不传宿主 Python 对象、HTTP 客户端、回调或额外宿主文件句柄；身份由会话绑定，拒绝请求自行切换 agent/episode/角色 | 宿主 broker |

允许的额外训练信号必须提前定义，例如练习终局的有限失败分类，并纳入输入协议。它不等于“只有传感器输入”。不向 agent 开放连续查询隐藏距离、物体身份或内部评分数值的接口。

`CAP-01`：基础能力是所选 episode/player 的 bench 函数目录、当前 agent SDK、输入条件、控制轨道和手部权限的交集，按协议/schema/控制器版本与能力清单绑定。bench 已有机器人说明、手部目标、姿态提示和腕相机等能力；客户端函数与玩家接线状态见[客户端说明](../README.md)。不能因底层字段存在就宣称模型已能调用。缺失或不兼容的必需能力在执行前明确报告，不静默换模式、换机器人或降级输入。目录、实际 wrapper 与模型工具说明必须一致。

`SEL-01`：学习模型只选择本阶段目录与预算允许的已实现练习 ID。可信宿主负责映射冻结版本并创建 episode；模型不提交本地 release 路径、任意物体初态或隐藏测试选择。planned 任务不能执行，validation/heldout 的槽位由冻结计划决定。

**动作与执行规则。**

默认使用固定的几何执行轨道，通过当前公开 `bench_functions_v1` 调用受支持的腕部、手部目标与 hold；[geometry_actions.py](../geometry_actions.py) 的旧增量接口只作为兼容构造方式。直接关节轨道另列条件，不能在学习中自动回退；当前棋牌双臂不支持 free 混合轨道。允许登记/取消合法落子意图，禁止直接改逻辑棋盘、伪造 committed 或写物体位姿。

| 接口类别 | 公开函数或操作 | Agent 侧语义 |
|---|---|---|
| 观察与计算 | get_robot、observe、read_camera、project_pixel、transform_points、query_ik、get_hand_presets、hand_preset | 不推进物理；hand_preset 返回姿态参数，不自动抓握。查询和成本分别记录 |
| 物理操作 | move_geometry、move_wrist、set_hand_targets、move_joints、hold | 仅暴露当前轨道支持的子集；宿主分配 action ID、绑定快照与权限、统一记账 |
| 动作查询与取消 | get_action、cancel_action | 查询原 ID；取消请求不等于已停止。未决动作对账期间不开放后续物理操作 |
| 生命周期 | get_result、finish_episode，以及创建/reset | 结果白名单投影；模型可提出结束/新练习请求，宿主按阶段与 bench 权限执行，不能直接重建会话或清零预算 |
| 双玩家附加操作 | /state、/intent、/result | 由绑定本方身份的宿主代理；棋牌与轮流操作分别使用其意图／结果合同，意图不推进物理 |

以上是统一 SDK 的约束范围；具体可用入口以[客户端说明](../README.md)和当前公开目录为准，不能从旧五工具 runner 推断全部能力。对提供结构化错误的路由，HTTP 非 2xx 需保留并校验 FunctionFailure 的 `error.code` 与可选 `context`，区分 permission_denied、stale_observation、unsupported_function/unsupported_capability、budget_exhausted 与 infrastructure_error。没有合法结构化正文时保留 HTTP/传输分类，不伪造 context；不把所有错误压成 API 故障，也不把未经校验的响应正文转给模型。

| 规则 | 要求 | 执行位置 |
|---|---|---|
| `ACT-01` | 每次动作绑定本回合公开观测序号；按各函数 schema 区分绝对目标与增量、world 与 flange、米与弧度，不复用错误坐标假设 | SDK 构造器与 bench 校验 |
| `ACT-02` | 仅控制运行合同中的机器人、活动手和关节；省略手遵循保持语义；不能靠提示词实现关节所有权 | 宿主权限检查及 bench |
| `ACT-03` | 不放宽限位、速度、动作窗口或原始物理配置；几何动作使用现有显式输入界限，不静默裁剪用户目标 | 宿主与 bench |
| `ACK-01` | 同时最多一个未决物理动作。宿主先生成 ID 并记录 payload hash，再提交；accepted 不等于执行完成 | 宿主动作账本 |
| `ACK-02` | 请求超时或回执丢失时锁住后续运动，按原 ID 查询/取消；不能改 ID 重发，不假定未执行。无法确认则记基础设施异常与执行未知，不记任务失败 | 宿主监督器 |
| `ACK-03` | 收到已确认的 failed/cancelled 后，若 episode 仍有效且已取得合法新快照，允许程序显式恢复；unknown/pending 的运动锁不能被 Python 捕获异常后绕过 | 宿主状态机 |
| `PHY-01` | 代码报错或撤销版本不回滚物理；不得写物体状态、重放物体轨迹、添加焊接、改变摩擦/碰撞或评分。reset 只由宿主按任务协议请求 | bench 与调度器 |
| `TIME-01` | observe/取图不推进物理；等待接触变化需要显式 hold/运动。闭环发生在公开动作边界，不宣称用户 Python 以 20 ms 或原生子步频率执行 | 运行时语义与记录 |
| `LOAD-01` | 模块导入和版本加载期间不允许物理操作；显式执行 cell/技能后才开放本 episode 的动作能力，reset/策略注册/预算修改不属于程序 API | 宿主调用状态 |

几何函数的 `timeout_sim_s` 是最大执行窗口，允许提前收敛；hold 的 `duration_s` 是显式定时保持，任务终态或换手仍可提前结束。时长、限位和容差取当前函数 schema、episode 配置与声明客户端限制，不把旧 runner 的 0.4–5 s 窗口硬套到所有函数。原生控制周期、请求窗口和实际步进分别报告。

宿主即使终止 Python 进程，也必须继续确认或收束未决机器人动作。查询与封存可以作为单列的清理开销，不能借清理继续任务运动。确认动作完成但无法获得合法新观测时也不得继续发动作。

**技能、记忆与阶段规则。**

`STAGE-00`：机械装配、实验室、厨房、书房和客厅共用任务已知 RSI：公布目标和公开规则 → 练习并修订技能 → 独立验证选版 → 冻结测试。默认一个任务、一个 learner、一次独立学习 run 一个库；任务差异由冻结合同绑定，框架不按场景复制。每个阶段共用[尝试、交互、模型与技能成本口径](../../../docs/agent_bench/skill_learning.md#task-rsi-mode)，结果按场景/任务/条件分开；阶段进度由各任务公开协议定义。planned 任务不能因采用此模式获得执行资格，跨任务经验须作为显式课程或导入条件声明。

客厅 Task1–3 为普通单 agent 任务，Task4 `tower_extraction` 为双玩家轮流抽塔，均保留 STAGE-00 的学习权限。Task4 的双方上下文、工作区、候选、验证与开发成本分别管理；共享物理会话中的动作串行化并归属实际玩家，换手不 reset 或清零成本。对抗玩法不自动触发棋牌室 task2/task3 的 STAGE-02 冻结比赛政策。该任务已有冻结工程发布、bench `/turn-games` 玩家接口、联合物理 worker 和 Agent 轮次适配器；当前公开 JSON 基线保留双方独立上下文。持久 Python 隔离与 RSI 调度仍待实现，不能从玩家接线推定完成。

`STAGE-01`：棋牌室 task0/task1 允许练习和任务已知 RSI，复用 STAGE-00 的版本与成本管理。task0 是普通 `/episodes` 单 agent 放置任务，每个 learner 使用独立物理 episode、上下文、技能库和预算，不等待对手。task1 是 `tic_tac_toe_3x3`，使用 `/board-games` 共享棋局和认证玩家轮次；允许学习不改变其双玩家语义。双方各自的上下文、库、开发记录和成本隔离，物理动作仍按本局轮次串行化。agent 可在练习预算内尝试、写改、验证和选版；task0 按普通任务结果，task1 按游戏结果计分，技能数量、修订次数和自测通过都不替代 bench 终局。权限政策不表示持久 Python、运行隔离或学习阶段调度已经实现。

`STAGE-02`：棋牌室 task2=`connect_four_5x5`、task3=`hex7x7` 使用冻结技能，不允许 RSI。宿主在首局前绑定双方各自选定的 bundle hash、来源事件、开发成本及兼容条件，整组比赛不换版；从 task0/task1 导入版本须明确记录，不能自动继承技能或任务资格。每局新建共享棋局和双方独立上下文。不开放 author、候选发布、验证选版、导入新库或经验写回，不按本组比赛反馈回到学习阶段改进后重测。task1/task2/task3 均走认证玩家路由；学习权限不同不改变棋种、轮次或动作所有权。

task2/task3 允许正常模型推理、局面估计、选择/组合冻结技能、计算本次目标与调用参数、更新本局状态及合法恢复。禁止新建、修订或覆盖可复用的技能/策略实现，禁止根据比赛反馈调优可复用策略参数、提示或检索资料；仅写在 scratch、同名函数或本局内存中也不例外。该限制也适用于冻结程序自行启动的参数训练。当前棋格目标、实时状态估计和冻结算法正常计算出的本次控制量不属于策略改进。通用临时编程权限不能放宽此边界，不能在比赛内启动候选改进—验证循环。

task0 的未决动作锁按独立物理 episode 管理；task1/task2/task3 对共享棋局统一串行化物理动作，不能只依靠两个客户端各自的锁。比赛中的一次换手不触发 reset，也不清除双方的临时上下文；一整局才是一个比赛 episode。

| 阶段 | 持久技能与经验 | 临时程序与当前状态 | 反馈去向 |
|---|---|---|---|
| practice | 可在自己的工作区修改，提交新候选版本 | episode 内可持续修改和执行 | 本实验后续练习可读取公开记录 |
| validation | 一次提交绑定同一只读 bundle | 每个验证/回归 episode 新建，结束后清空 | 整批结束后把约定验证反馈给学习 agent |
| 普通任务 frozen evaluation | 携入的 bundle、参数、长期笔记与索引只读 | 允许每回合临时编程、模型帮助和恢复；结束后清空 | 当前回合可见已有公开结果；不进入后续测试回合或学习链 |
| 棋牌室 task2/task3 | 整组比赛绑定选定版本及其明确来源；无学习写改与选版权限 | 仅 STAGE-02 的推理、计算、冻结技能调用与合法恢复；不修改技能实现 | 当前局可用公开反馈；不进入下一局或学习链 |

当前范围不开放跨测试回合改库的 online adaptation 条件；它不是 task2/task3 的可选开关。task0/task1 的 practice/validation 循环属于学习预算，冻结后的评价及 task2/task3 比赛均不回流同一学习链。

`STAGE-03`：阶段切换只由宿主执行。发布只固定内容；验证只运行本批绑定的候选并返回允许的证据；选版不追改已执行回合；冻结同时绑定版本、来源、模型/工具条件和测试计划。有效验证失败可以回到 practice 修改，基础设施中断保持待验证；进入最终测试后没有回到同一学习链修改再重测的边。预算结束使用协议预定的版本或空库并记录未达标，不由宿主补写解法。人工调试介入另记来源和新条件，不能混入自主 RSI 成绩。

`VAL-01`：候选验证执行者使用新进程/上下文，只读当前 bundle、固定公开 SDK、任务与当前观测；不读作者调试对话、未发布草稿或其他验证回合。模型可以按固定预算做本回合临时推理和代码修复，但这些修改留档且不写回候选；验证中覆盖或替换候选实现时，证据应标明“候选加临时修改”，不能称未改原技能的独立复现。修改的因果收益需另由预登记对照判断。所谓纯代码技能验证须另设关闭模型帮助的条件。

从 task0/task1 显式选用技能参加 task2/task3 时，选版验证的代码权限须与 STAGE-02 对齐；验证任务及门槛仍取 bench 协议，不要求先跑完整比赛。发生临时技能修复的执行仅作为开发诊断，不使原候选获得冻结执行资格；如需采用修复，须在获准的练习预算内发布新候选后按冻结权限重新验证。来源任务成功不自动证明目标棋种资格。有效任务结果与版本验证分别保留。

`VAL-02`：证据区分源码/接口自测、同初态复现、新初态验证、最终冻结评价和显式跨任务迁移；它们不是自动晋级的等级。一个 bundle 的成功不能给其中未调用的技能逐一授予资格。技能自写 verifier 可以基于公开观测给出辅助判断，但必须记录来源与不确定性，不能替代 bench 裁判；自测应覆盖相关边界/反例，不以自测数量当能力分数。

`MEM-01`：每次 reset 创建新 Python namespace、消息上下文和观测绑定。跨回合仅按阶段权限携带显式导出的源码与 JSON 经验；不恢复旧进程或 Python pickle，不把上回合的实时物体估计重新绑定为本回合当前观测。允许保留带来源、时间和不确定性的历史估计或场景假设，实际动作仍须绑定当前公开快照。目标状态、实际观测和长期假设分开表示。

`request_replan` 结束当前 cell 并把执行权交回宿主，不承诺恢复 Python 调用栈；后续 cell 继续使用本回合 namespace，需恢复的游标放入显式 episode state。它不重置预算，也不解除任何未决动作锁。

`VER-01`：每个 bundle 固定源码哈希、参数、描述、长期笔记、检索索引、入口、精确依赖及适用机器人/装配/控制器/观测条件。一次 trial 绑定一个 bundle，不热换版本；阶段允许的临时 cell 改写必须留档，尚未提交的代码不冒充已验证技能。task2/task3 的允许范围以 STAGE-02 为准，留档不使被禁止的技能修改合法化。

`VER-02`：`candidate/tested/selected` 表示需有宿主记录支持的事实与选择关系，不写入不可变 bundle，也不构成只能前进的单向状态。tested 表示有特定条件下的有效验证证据，不等于通过；selected 只影响后续 trial 的默认版本。验证计划和门槛来自 bench 运行协议；agent 的自测和成功自述不能替代 bench 结论。修改依赖触发相关回归，失败与旧版本保留。

`MEM-02`：跨场景、跨实验或双玩家复用必须显式导入固定 bundle，并记录开发来源和成本；不读取全局实时更新的技能库。新版本或新场景的兼容性检查通过，仅允许尝试，不代表任务资格。

跨回合可保存从公开交互中获得的场景知识和自己的感知/规划代码；固定坐标并非自动违规，其适用范围由新初态测试决定。约束保护测试隔离，不用代码风格决定是否“真正学习”。

**预算与错误反馈。**

`BUD-01`：运行前明确学习阶段、验证批次、episode 和 cell 的预算归属；所有请求进入同一可信账本，任务预算与基础设施重试额度分别配置，不允许通过换函数、重启 cell、reset 或创建候选绕过计量。额度由实验配置确定，不在本约束中写死“每技能最多几次模型调用/动作”。

宿主在请求前、模型或工具响应返回后都重新检查期限与剩余额度；迟到回答不能继续发动作。动作时长预留与实际已确认仿真消耗分别记录，不能用最大窗口冒充实际执行时间。

| 必须声明的资源 | 计量与停止行为 |
|---|---|
| 计划槽位、执行 attempt、reset 与验证提交次数 | 初始化异常与重试全部留档；故障补跑关联原槽位，次数受单独额度约束，不自动记成有效任务失败 |
| 模型尝试、上下文与输出配置 | 记录每次实际请求、失败和可得 usage；不得自动切供应商、模型或推理强度 |
| primitive 尝试、HTTP 提交、确认完成数 | 分开记录，沿用识别到物理请求即计尝试的语义；无效参数与 stale 请求不能获得免费搜索 |
| 每动作、episode、学习阶段的仿真/墙钟预算 | 已启用资源限制仍生效；实际总墙钟包含截图、计算、网络和归档，另记可核验的故障等待时间与任务计时 |
| 每 cell CPU/wall、内存、进程数量、输出/RPC 大小及 scratch 配额 | 外部监督器强制有限上限；超限停止程序并收束未决动作 |

总 sim/wall 时限只有字段明确允许时才能显式设为 null；次数与 cell 资源限制仍生效。总 wall 为 null 时，仍须配置有限的累计 cell/计算预算和请求配额，覆盖只读查询；不能靠无限重启 cell 或查询绕过单次限额。输出 token 上限可以显式关闭并按供应商协议省略字段，不伪造大上限。未知 usage 保持未知；模型端超时不能当作零成本或未请求。agent 不能在失败后自行放宽预算。

故障耗费的请求、token、墙钟和 GPU 资源照实记录，但资源账本不直接决定任务成败。bench 需规定故障等待如何暂停任务计时、恢复或补跑，由可信宿主按证据执行，agent 自报故障不能获得额外额度；服务无法支持暂停且故障导致时限耗尽时，标为受基础设施影响的未完成，不能转换成 agent 任务超时失败。Micu 瞬态异常默认等待 10 秒后重试同一逻辑请求，未配置次数上限时持续到恢复、已声明预算耗尽或主动取消，不额外引入默认暂停；若显式配置了重试额度则遵守，永久认证/配置错误不套用瞬态重试。只读 HTTP 与物理动作恢复分别使用各自合同，不能因此重放物理动作。已取得的观测、模型回答和实际动作不能因故障补跑从学习成本与暴露记录中消失。

`ERR-01`：自己代码的语法、类型、断言和数值错误允许返回本工作区的源码行号与清洗后的 traceback，便于真实调试；不要把所有错误压成无用的 generic failure。宿主/bench 的异常只返回公开类型与允许细节，不包含内部路径、凭据、隐藏数据或原始服务响应。一次程序失败不能掩盖此前已执行动作。

`ERR-02`：模型 API 或 bench API 的网络中断、服务不可用、外部限流和无法确认的超时不计 agent 任务失败。执行健康与任务结果分开记录，例如 `infra_error` 与 `task_outcome=unknown`；字段名由 bench 合同确定，不能用 `success=false` 代替未知。归因使用请求/回执和服务证据；原因不明时保持未知，不能只凭 HTTP 状态码把非法动作、自身代码错误或模型正常返回但决策错误都归为基础设施异常。已确认且证据有效的权威终局结果不因后续 API 故障被覆盖。

| 故障位置 | 恢复与结果语义 |
|---|---|
| 模型请求或只读 API 暂时不可用 | 模型瞬态故障默认固定 10 秒重试；只读请求按其传输合同重试。模型配置不变，逐次记录成本与未知 usage；模型逻辑请求绑定请求 hash、上下文/观测版本和生成 ID，只采用一个有效响应，恢复前重新核对快照；迟到/重复响应只留档，不触发额外代码或动作 |
| 动作已提交、回执丢失或取消尚未确认 | 查询原 action ID 并确认终态；未收束前不重新提交动作或重建同一物理会话，无法确认时保留执行未知 |
| 创建 episode 或 reset 的响应丢失 | 按创建/reset 请求身份查询确认，或使用 bench 明确保证的幂等协议；这些操作有副作用，不能作为只读请求盲目重试 |
| episode 因外部故障无法继续 | 保留原 attempt；由可信宿主按 bench 协议恢复，或确认原会话已停止并隔离后补跑同一冻结槽位，不换容易初态 |
| 测试/验证需要补跑 | 绑定原技能版本、模型配置和初态；新 attempt 使用干净上下文，不能利用中断尝试修改技能。每槽位取首个有效结果，不能择优；有效成功或失败均不触发故障补跑 |

故障补跑不能被当成额外学习机会；practice 中已经产生反馈或代码修订的 attempt 仍计入开发历史，其后续执行按 bench 的学习协议处理。尚未拿到有效验证结果的候选保持待验证，不因 API 故障被判技能失败，也不能算通过。

**结果与证据规则。**

`EVD-01`：技能入口返回 `completed/failed/needs_replan` 等局部状态。程序完成、动作完成、接触非零、模型 stop 均不直接证明任务成功。权威任务结果来自 bench；正式有效性还需其物理和归档证据，agent 无权改写。

`EVD-02`：宿主追加保存模型实际可见输入、原回答、每个 cell 的源码与 hash、选定 bundle、观测引用、所有动作请求/回执、候选更替、版本来源、预算和错误分类。agent 可选择 `report` 内容，但不能删除强制执行记录或用后一次成功覆盖前一次失败。公开结果按 schema 白名单投影，不能把整个终局原始字典作为模型上下文。

`EVD-04`：反馈分层保存模型响应/解析、函数校验、物理动作、公开阶段、任务终局与执行健康。保留原 code、权威证据引用和归因来源，自动可确定的事实与模型/人工诊断分开；原因不明保持 unknown。阶段事件需由 bench 定义触发、持续时间、回退条件与公开范围，记录首次到达和结束时是否仍成立，不能将曾经达到的进度冒充终态成功。动作执行成功、计划执行无异常与任务完成是不同指标。

`EVD-03`：基础设施异常、物理/评分证据失效、agent 失败和未执行槽位分开统计。全部计划槽位、每次 attempt 和真实消耗保留；任务成功率只在有效且有权威终局的槽位上计算，包含 bench 按协议确认的正常预算耗尽、主动放弃或无进展等失败，不能只统计自然完成。未判定槽位不算失败，同时报告有效覆盖数/计划数及各类未完成数，无有效结果时成功率为不可用。正式 Cold/Warm 配对比较只使用双方均有效的配对槽位，并报告缺失配对；不能把部分覆盖写成完整测试成绩，也不能通过事后改归因排除真实任务失败。框架源码和技能资产分别固定；改变框架或控制器需要新的运行条件，不能伪装成一次 agent 技能更新。

**棋牌室新合同的接入约束。**

以下消费现有 [bench 玩家合同](../../../docs/agent_bench/card_room_rules.md)，不复制游戏规则。task0 使用普通 `/episodes`；task1=`tic_tac_toe_3x3`、task2=`connect_four_5x5`、task3=`hex7x7` 使用 `/board-games`。task0/task1 允许练习 RSI，task2/task3 遵守 STAGE-02。bench 已有玩家身份校验、函数分发和三棋种原生短链路；Agent 接线状态见[客户端说明](../README.md)。短链路不代表模型抓放、整局成功或学习调度已实现。

| 规则 | Agent 侧要求 |
|---|---|
| `GAME-01` 身份 | 创建得到的两个 Bearer token 仅由可信传输宿主持有；模型/技能只见公开 player/hand/joint binding，不能在 prompt、bundle、scratch、普通日志中保存令牌。认证媒体下载也经宿主代理；不私自裁掉合同允许看到的对方机器人观测 |
| `GAME-02` 共享状态 | 两人共用 match/episode 的 action ID 空间和 bench 预算；宿主分配带玩家前缀的 ID，分别累计双方模型/查询成本。工具和生成代码不能切换身份或绕过玩家路由；bench 未计量的模型成本由 agent 宿主负责 |
| `GAME-03` 轮次交接 | 新动作/意图须是当前玩家。`cancelled/board_turn_changed` 表示裁判交棒，不是技能失败或控制器到位；共享宿主先核对旧动作终态及匹配公开快照，再放行下一方。换手保留整局上下文，下一方只按新快照决策 |
| `GAME-04` 意图与恢复 | placement/cancel 只改意图，等待稳定必须实际 hold/动作。意图 `attempt_index` 单独计，不算任务 attempt；重选/取消/恢复、物理 commit 和成功落子交互成本分别记录。原 ID 查询/取消服从己方所有权；创建响应丢失不能盲重建比赛 |
| `GAME-05` 结果 | 从玩家 `/result` 读取 BoardGameResult，先看 board_game.status.outcome：win 时比较 winner 与本方 player_id 得出胜/负，draw 才记和；truncated/aborted 单列，不能从 winner=null 推和棋。普通 get_result 的 EpisodeResult.outcome="success" 只代表裁判达成胜负或和棋终局。另列物理有效性和执行健康，未完成或 API 故障不判输；保留已接受终局事实，证据不足时不得计为有效胜局 |
| `GAME-06` task0 路由与目标 | 创建普通 `/episodes` 单 agent 会话，读取 `ready['task']` 或 `/episodes/{episode_id}/task` 的本回合目标与公开规则；`/tasks` 不包含实际目标格。三枚黑子到三个不同目标格可任意分配，不要求棋局意图。不得用比赛会话、隐含对手或宿主代替对方行动模拟 task0 |
| `GAME-07` task1 学习 | 使用井字棋 `/board-games` 会话并保持玩家认证、轮次与动作权限；允许练习与 RSI，双方技能库和开发记录仍隔离。学习阶段与版本切换须由可信宿主安排，不绕过未决动作锁；这不是当前函数运行器已提供持久 Python/阶段调度的声明 |

task0 按普通任务报告完成率、有效覆盖和学习成本。task1/task2/task3 按 learner 的 win/loss/draw、有效完成局数/计划局数与未完成原因呈现，配对互换颜色时保留各色成绩；task1 的练习/验证成本另列，不能把持续改库的练习成绩当冻结策略成绩。task2/task3 整组比赛固定对手版本和双方 bundle，各局初态按预定计划绑定。一次 commit 是一手棋，不是整局成功。`GAME-05` 的玩家结果规则只在 board-game task 中优先于普通任务成功率口径。

<a id="living-room-adapter"></a>

**客厅任务与机械任务接入。**

机械 L1–L5 是 `implemented` 场景候选，按普通单 agent `/episodes` 使用共享公开函数。`implemented` 只表示目录可加载，`prepared_unvalidated` 与其有界接触证据不构成机器人操控资格。公开规则由 bench 投影和绑定，不让模型读取含私有 reset／评分的本地任务文件。

客厅 Task1 `remote_operation`、Task2 `water_pouring`、Task3 `tower_building` 为单 agent，Task4 `tower_extraction` 为两玩家对抗；四项均为 `implemented` 工程候选。Task1–3 通过普通 `/episodes` 和共享函数适配器接入，Task4 通过认证 `/turn-games` 适配器接入。显式 `--family living_room` 时四项均核对 catalog 当前冻结发布的哈希与创建响应。Task4 保留独立的 `TurnIntent`／`TurnGameResult` 合同，不能作为普通 episode 或 `/board-games` 棋种发送。发布保持 `prepared_unvalidated`／`physics_accepted=false`，可加载与短链路证据不等于完整物理任务资格。

Task4 的公开玩法为交替抽块、放入己方收集区，不重新叠顶，导致倒塌的一方输；完整合法动作与判定仍消费 [Task4 规则](../../../scenes/workrooms/living_room/tasks/tower_extraction/README.md)。front/rear 两套 FR3 都装原始右 SHARPA，bench 的 `player_0`／`player_1` 分别绑定这两台机器人；双方的关节、frame、相机和动作身份须由各自机器人绑定，不能套用棋牌室单个双手装配的左右手 schema。双方同时最多一个未决物理动作；确认交接前不允许另一方运动，缺失证据、API 故障与已确认胜负分别记录。玩家令牌、对方私有上下文和学习库不进入本方模型输入。

轮次以公开 `turn_game.current_player_id` 和 `turn_index` 为准，一轮可以包含多次意图、查询、抓取、调整与 hold；只有原生裁判确认交接才切换模型。`cancelled/turn_changed` 是交接收据，不是目标到位或另一方自动取得运动权限；旧动作终态与匹配快照先完成对账。换手保留整局双方各自历史，不重建上下文、重置预算或技能库。`TurnGameResult` 的 completed 胜负／平局与 interrupted 分开；无赢家的中断、预算未完成、无效初始化和证据缺失不计平局或玩家失败。当前 Task4 的原生 `invalid_reset_not_stable` 阻断仍保留，不能靠客户端动作、重置或修改裁判绕过。

<a id="laboratory-adapter"></a>

**实验室五项任务接入。**

`--family laboratory --task task1`–`task5` 分别选择样本分类、试管入架、开盖复盖、颗粒称量和活塞移液。五项使用同一单臂 FR3 + 右 SHARPA 的普通 `/episodes`，两张台面不是两名玩家；拒绝 `/board-games` 或 `/turn-games` 的任务声明。显式 family 绑定 catalog release，创建响应、公开任务规则与终局身份继续核对；省略 family 的 canonical ID 保留 service-selected 历史发布语义，实际 release 以回执为准。

五项均采用 `STAGE-00` 的任务已知 RSI 权限，按任务、learner 和独立 run 管理技能与成本。当前只接公开 JSON 函数基线，持久 Python、隔离及完整练习调度仍待实现。模型可读公开规则、粗粒度裁判阶段和合法观测；不能通过宿主 catalog、原生 observer 或实验记录补入真实物体位姿、接触、颗粒身份、水量账本与私有中间评分。不得新增任务专属的直接改水量、移动器具或生成成功证据的函数。

本次场景资格只覆盖初始化和物物可行性，手物交互由数采负责。试管自由投落尚无稳定落座资格；移液采用声明的体积守恒近似，未施加水重与射流反作用。Agent 接线与 CPU 替身检查不升级这些物理结论，也不改变冻结 manifest 的准备状态。

**必须验证的约束行为。**

下表是实现后的验收要求，不是当前已通过的测试：

| 情形 | 期望行为 |
|---|---|
| 定义函数，下一 cell 继续调用；有界预算内运行 while/NumPy | 允许，函数与变量在当前 episode 保留 |
| Python 报错后修复；此前动作已确认失败 | 返回可定位的自身代码错误；新快照有效时允许显式恢复 |
| 写作模型或执行程序读取私有目录、环境凭据、其他 episode 缓存或通过链接逃逸 | 实际访问被阻断，不仅是提示词拒绝 |
| tactile-off 从动作 contact_history 或历史缓存取触觉；RGB-only 调 point_at | 一致拒绝或移除，不通过另一条输入路径泄漏 |
| 发送另一只手目标、未公开控制字段、stale 观测或重复改内容的 action ID | 拒绝且不推进物理，按协议记录尝试 |
| POST 已发送但响应丢失，或收到 accepted 后 worker 阻塞 | 保持原 ID 查询/收束，锁住后续动作；无自动重发 |
| 模型/只读 API 持续不可用并耗尽故障重试额度 | 保留基础设施异常与任务未判定，不写任务失败、不把未知 usage 填零 |
| 任务已有有效终局后取图失败；验证途中故障且无终局 | 前者保留原任务结果；后者保持待验证，按固定协议恢复或补跑 |
| 无限循环、巨大数组、过量输出或请求模型帮助时预算已耗尽 | 宿主可靠终止；无额外模型/动作越过预算；既有动作记录保留 |
| reset 后尝试读取上回合变量，或后续 heldout 槽检索前一槽经验 | 不可读取；冻结 bundle 本身仍可用 |
| 普通任务评测临时写函数与调用模型，或尝试把它发布到长期库 | 前者按预算允许，后者拒绝；回合结束清临时状态 |
| task0 首次尝试即取得有效成功，未产生多个技能修订 | 按 bench 记任务成功，记录实际成本；不强迫失败、改库或增加版本数 |
| task2/task3 推理选格、计算当前动作参数、调用冻结恢复技能 | 按公开规则和预算允许；换手保留本局状态 |
| task2/task3 在 scratch/内存重写技能、申请候选验证，或两局之间换库 | 拒绝；只读文件并不足以证明禁止 RSI，须关闭学习工具并核验实际执行代码与绑定版本 |
| 只有一种输入/手型被实现，却请求另一种能力 | 执行前明确报不支持，不自动降级或借用独立后端 |
| 候选在干净上下文中需要临时修复才成功，或存在未调用的库条目 | 记录修复及实际调用证据，不给原技能或未用条目泛化资格 |
| hand_preset 仅返回参数、intent 重选、一次 cell 执行多次物理函数 | 分别记查询、意图与真实动作，不按外层工具包装压缩交互数 |
| 棋牌动作因 board_turn_changed 取消；胜者与当前 Agent 不同 | 前者正常交棒并完成对账，后者按玩家结果记负，不读取普通 success 作为获胜 |
| 尝试用比赛会话运行 task0，或把 token 写入模型输入 | task0 必须走普通 episode；令牌不进入公开输入/技能/日志 |
| task1 学习阶段写改技能或切换候选 | 在获准阶段和预算内允许；仍遵守 board-game 玩家身份、共享动作锁、轮次和版本留证规则 |

现有 [program.py](../program.py) 是一次性受限解释器，[visibility.py](../visibility.py) 是可信客户端输入投影，[InteractionSession](../interaction.py)负责动作构造与计数；它们不等于上述完整运行时隔离。新的 agent 侧宿主需要在公开 API 上适配并验证这些行为。未实现的规则不能标为已强制执行；隔离不完整的运行只作为明确标注的可信开发诊断。
